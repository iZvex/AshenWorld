# Границы подсистем и точки расширения

Документ девятого этапа. Он отвечает на два вопроса: **что кому можно** внутри игры сегодня и **куда встраивается онлайн**, когда он появится. Онлайн не реализована: в коде нет сетевых классов, аккаунтов и облачных сохранений, разрешение `android.permission.INTERNET` в APK отсутствует, игра полностью играбельна в авиарежиме.

Смысловые контракты методов описаны в [`api.md`](api.md), полный список сигнатур — в [`api_reference.md`](api_reference.md).

## 1. Карта слоёв

| Слой | Модули | Отвечает за | Состояние |
|---|---|---|---|
| Данные | `data/balance.json` | Все числа, тексты, награды, цены, шансы | Версионируется полем `version` |
| Каталоги | `combat_catalog`, `campaign_catalog`, `mode_catalog`, `equipment_catalog`, `progression_catalog`, `save_catalog`, `presentation_catalog` | Чтение и проверка баланса, чистые функции | Состояния нет |
| Логика | `combat_system`, `combatant`, `combat_formulas` | Бой одного этапа | Живёт в `CampaignState.system` |
| Состояние | `campaign_state`, `equipment_state`, `progression_state` | Игровые данные и правила | Единственный источник истины |
| Сохранение | `save_manager`, `profile_manager` | Диск, конверт, контрольная сумма, офлайн-время | Профиль версии 8 |
| Представление | `presentation_catalog`, `ashen_style`, `ashen_audio`, `effect_pool` | Тема, звук, эффекты, чтение настроек оформления | Только визуальные параметры |
| Экран | `main.gd`, `scenes/main/main.tscn` | Склейка логики и интерфейса | Никакого игрового состояния |

## 2. Разрешённые направления зависимостей

```
main.gd ──► campaign_state ──► combat_system ──► combatant / combat_formulas
   │              │  │
   │              │  ├──► equipment_state ──► equipment_catalog
   │              │  └──► progression_state ──► progression_catalog
   │              ├──► campaign_catalog / mode_catalog
   │              └──► save_catalog
   ├──► save_manager / profile_manager
   └──► presentation_catalog / ashen_style / ashen_audio / effect_pool
```

Правила:

1. Стрелка означает «может вызывать». Обратные вызовы запрещены: логика не знает про `main.gd`, интерфейс не лезет во внутренние поля состояния.
2. Каталоги вызывают только друг друга и никогда — состояние.
3. `combat_system` не знает ни о кампании, ни о сохранении: он получает данные в `_init` и сообщает о событиях сигналами.
4. Слой экрана не пишет файлы и не считает формулы; он читает `get_summary()` и вызывает методы.
5. Файловый ввод-вывод есть только в `scripts/save/` (и в `game_config.gd`, который читает баланс при старте).
6. Сетевых классов нет нигде; запуск в авиарежиме — обязательное условие приёмки.

## 3. Что проверяет сборка

Эти границы не только описаны, но и проверяются автоматически в `tools/validate_repo.py`:

- нет `HTTPRequest`, `HTTPClient`, `WebSocket`, `StreamPeerTCP`, `PacketPeer`, `NetworkedMultiplayer`, `ENetMultiplayerPeer`, `WebRTCMultiplayerPeer` и `MultiplayerAPI` ни в одном скрипте;
- `FileAccess`/`DirAccess` в `scripts/` встречаются только в `scripts/save/save_manager.gd`, `scripts/combat/combat_catalog.gd` и `scripts/core/game_config.gd` — запись на диск живёт в слое сохранений, чтение баланса — в двух загрузчиках;
- скрипты логики и состояния (`scripts/combat`, `scripts/campaign`, `scripts/equipment`, `scripts/progression`, `scripts/save`) не упоминают `Control`, `Node2D`, `AshenStyle`, `main.gd` и `res://assets` — комментарии при проверке отбрасываются;
- каталоги (`*catalog.gd`) не заводят переменных верхнего уровня: только константы и `static func`, поэтому у них нет глобального кеша;
- `main.gd` не содержит `FileAccess` — чтение и запись идут только через `ProfileManager`/`SaveManager`;
- `docs/api.md` описывает обязательные контракты (`get_summary`, `export_state`, `import_state`, `advance`, `STATUS_BATTLE`, `format_version`) и все подсистемы, а `docs/boundaries.md` — четыре шва и офлайн-требования;
- справочник `docs/api_reference.md` актуален (`python3 tools/api_report.py --check`), проверка запускается из `validate_repo.py` и из CI.

## 4. Швы для будущего онлайна

Онлайн добавляется **четырьмя адаптерами**, каждый из которых вставляется в уже существующую границу. Игра при этом остаётся играбельной офлайн: адаптер по умолчанию — локальный.

### 4.1. Источник контента (`CatalogSource`)

- **Сегодня:** `data/balance.json` читают каталоги; версия баланса сохраняется в профиле (`balance_version`).
- **Шов:** каталоги уже принимают `balance: Dictionary` параметром, а не читают файл сами. Значит, источник можно заменить на «баланс с сервера + подпись версии», не меняя ни один вызов логики.
- **Контракт:** набор разделов баланса, `version`, `save.format_version`; отсутствие разделов = ошибка загрузки, а не тихое «пусто».
- **Что нельзя менять:** интерфейс состояния каталогов (`static func`, только чтение) и правило «все числа в балансе».

### 4.2. Владелец боя (`BattleAuthority`)

- **Сегодня:** бой считает `CombatSystem` на устройстве, детерминированно по `seed`.
- **Шов:** `CampaignState.start_stage()` — единственное место создания боя, а весь обмен с ним идёт через шесть методов (`advance`, `use_skill`, `get_cooldown_remaining`, `spawn_next_enemy`, `set_pet_data`, `get_state`) и девять сигналов. Серверный («авторитетный») бой встраивается подменой реализации за этим контрактом: тот же набор сигналов, те же статусы.
- **Контракт:** сигналы и `status` кампании; независимость от `performance`-настроек (`advance(delta)`), отсутствие пауз по сети.
- **Что нельзя менять:** `CampaignState.STATUS_*`, состав `last_reward`, правило «победа начисляется один раз».
- **Требования к сетевому варианту:** идемпотентность шага (повтор того же `delta` не должен задваивать награду), версия протокола в конверте, обработка разрыва без потери прогресса, тот же `seed` для воспроизводимости при разборе жалоб.

### 4.3. Бэкенд сохранений (`SaveBackend`)

- **Сегодня:** `SaveManager` пишет конверт с контрольной суммой FNV-1a в `user://ashenworld_profile.json`, `ProfileManager` считает офлайн-время.
- **Шов:** запись и чтение сосредоточены в `SaveManager.load_profile()` и `SaveManager.save_profile()`, формат конверта — в `build_envelope()`/`canonical_envelope()`. Облако добавляется как второй бэкенд с тем же конвертом; локальный файл остаётся кешем и офлайн-источником.
- **Контракт:** `{"valid", "status", "payload", "version", "saved_at"}`; статусы `new/loaded/migrated/recovered/corrupted/future`; профиль версии 8 и миграции из [`saves.md`](saves.md).
- **Что нельзя менять:** версия формата без миграции, контрольная сумма, поведение «будущая версия → не затирать профиль».
- **Требования:** разрешение конфликтов по `saved_at` и `checksum`, запрет на потерю локального прогресса при ошибке сети, отсутствие токенов в открытом виде (секреты — только в защищённом хранилище устройства).

### 4.4. Внешний профиль и рейтинг (`PresenceSource`)

- **Сегодня:** никнейм берётся из `presentation.interface.hud.nickname` (по умолчанию класс героя), рейтинг считается локально: `уровень × 100 + лучший этап × 10 + боевая мощь`.
- **Шов:** рейтинг и никнейм — только отображение в `ProfilePanel`; формула живёт в `main.gd._rating_value()`, а данные — в `get_summary()`. Сетевая таблица лидеров подключается как дополнительный источник этих двух значений.
- **Контракт:** рейтинг остаётся целым числом, никнейм — строкой; отсутствие сети не должно менять вёрстку и ломать профиль.
- **Что нельзя менять:** панель профиля не должна блокироваться до ответа сети, офлайн-рейтинг обязан считаться всегда.

## 5. Порядок внедрения (когда онлайн появится)

1. **Источник контента.** Сначала версионируемый баланс и проверка подписи — без него нельзя гарантировать одинаковые правила у клиента и сервера.
2. **Бэкенд сохранений.** Синхронизация профиля, конфликты, офлайн-кеш. Самое ценное для игрока — не потерять прогресс.
3. **Владелец боя.** Только после 1–2: серверный бой без стабильного контента и сохранений бессмыслен.
4. **Профиль и рейтинг.** Таблицы лидеров, никнеймы, модерация имён — последний шаг, потому что он не влияет на офлайн-игру.

## 6. Чек-лист готовности к онлайну

- [x] Все числа и тексты вынесены в `data/balance.json`, версия баланса сохраняется в профиле.
- [x] Логика не зависит от сцены и интерфейса, бой проверяется без запуска игры.
- [x] Единственный источник истины — `CampaignState`; интерфейс не хранит состояние.
- [x] Детерминизм: явный `seed` у боя, экипировки и прогрессии.
- [x] Сохранение с версией, контрольной суммой, миграциями и защитой от откатов (temp-файл).
- [x] Публичный API описан и автоматически сверяется справочником.
- [x] Зафиксированы границы записи на диск и отсутствие сетевых классов.
- [ ] Серверный протокол, авторизация, античит — отдельный этап, в текущей версии не начат.

## 7. Что делать нельзя

- Добавлять сетевые вызовы в игровой цикл или в сохранение «на всякий случай».
- Считать награды/урон на сервере и на клиенте по разным формулам: формулы обязаны приходить из одного баланса.
- Хранить игровое состояние в `main.gd` или в узлах сцены.
- Менять формат сохранения без миграции и без роста `format_version`.
- Обходить `SaveManager` прямой записью в файл из интерфейса или тестов.
- Дублировать коэффициенты баланса в коде «для скорости».
